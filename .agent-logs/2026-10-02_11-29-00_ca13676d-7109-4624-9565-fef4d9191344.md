The failure is **not** from missing Supabase config or a bad schema. Prisma **`generate`** is trying to replace the Windows query engine binary with a rename:

`query_engine-windows.dll.node.tmp…` → `query_engine-windows.dll.node`

Windows returns **`EPERM: operation not permitted`** when that target file is **already open / locked** by another process, so the rename is blocked.

## Usual causes on Windows

1. **`npm run dev` still running** — Next.js loads Prisma and keeps `query_engine-windows.dll.node` loaded. This is the most common case.
2. **Another build or `prisma generate`** in a second terminal.
3. **Antivirus / Windows Defender** briefly locking `.node` files under `node_modules\.prisma\client\`.
4. Less often: another Node process, or the IDE indexing that folder.

## What to do

1. Stop the dev server (and any other `node`/`next` for this project) — Ctrl+C in that terminal.
2. Run `npm run build` again.

If it still fails:

- Close extra terminals running this repo.
- Retry once; if needed, delete `node_modules\.prisma` and run `npx prisma generate` (with dev still stopped).
- Temporarily exclude the project folder from real-time antivirus scan if it keeps happening.

**Summary:** Something (usually **dev server**) is holding Prisma’s engine DLL while `prisma generate` tries to overwrite it during `npm run build`. Stop those processes, then rebuild.

Here’s how redirects work in this repo and what you need for production.

## Short answer

**In-app redirects are not tied to localhost.** They use **relative paths** (`/login`, `/onboarding`, `/studio`, `/home`, etc.), so they follow whatever host the user is on.

**The only localhost-specific piece is env config** — mainly `AUTH_URL` in `.env` (and what you set in Vercel). That drives **NextAuth / Google OAuth absolute callback URLs**, not the internal `redirect()` calls.

---

## What uses relative paths (works on any domain)

| Area | Behavior |
|------|----------|
| **Middleware** (`middleware.ts`) | Protects `/home`, `/studio`, `/focus`, `/create/*`; unauthenticated users go to sign-in page `/login` (from `auth.config.ts` `pages.signIn`). |
| **`require-user.ts`** | `redirect("/login")`, `redirect("/onboarding")` — path only. |
| **Google sign-in** | `signIn("google", { callbackUrl: "/onboarding" })`. |
| **Evaluator** | `callbackUrl: "/studio"`; after success, `window.location.href = "/studio"`. |
| **Sign out** | `callbackUrl: "/login"`. |
| **Onboarding** | `redirect("/home")` when already onboarded. |

No `http://localhost:3000` in application TypeScript — only in **README** and **`.env.example`** as the local dev example.

---

## What depends on `AUTH_URL` (you must change for prod)

`AUTH_URL` is listed in `lib/auth-env.ts` as required for “full” Google auth, but the app does **not** concatenate it in code. **NextAuth v5** reads it from the environment when building OAuth URLs.

Your config also has:

```49:50:lib/auth.config.ts
export const authConfig = {
  trustHost: true,
```

So on Vercel, NextAuth can also use the **incoming request host** when `AUTH_URL` isn’t set — but you should still set `AUTH_URL` explicitly in production to avoid surprises.

| Environment | Set `AUTH_URL` to |
|-------------|-------------------|
| Local | `http://localhost:3000` (your current `.env`) |
| Production | `https://your-production-domain.com` (no trailing slash) |

**Google Cloud Console** must list **both** redirect URIs if you use both environments:

- `http://localhost:3000/api/auth/callback/google`
- `https://your-production-domain.com/api/auth/callback/google`

(README documents this as `{AUTH_URL}/api/auth/callback/google`.)

---

## Production checklist

1. **Vercel (or host) env**
   - `AUTH_URL` = production origin (`https://…`)
   - Keep `AUTH_SECRET`, DB, Google client vars aligned with prod.

2. **Google OAuth**
   - Add the **production** authorized redirect URI (see above).

3. **Evaluator link** (if used)
   - Share `https://your-domain.com/evaluator?token=…` (comment in `.env.example` uses `{AUTH_URL}` — you build that URL yourself; nothing in code hardcodes localhost).

4. **No code changes** are required for internal redirects when you deploy — only env + Google console.

---

## Optional gotcha

If Google sign-in still sends you to `localhost` after deploy, **`AUTH_URL` (or Google redirect URIs) is still pointing at local**, not the app routes. Fix env and Google credentials, not the React redirect paths.
